# 验收标准与工作方式（必读，第七份）

## 1. 每一轮都必须留下证据

做完一块，就在 `docs/进度.md` 追加一条，格式固定：

```
## 第 N 轮 · <日期>
- 做了什么：<一句话>
- 怎么验的：<真实跑过的命令 / 点过的界面 / 截图路径>
- 结果：<通过 / 失败原因>
- 下一步：<紧接着做什么>
```

**没写证据的一律算没做。**

## 2. 自测清单（每次交付前自己过一遍）

后端：
- [ ] 服务能起来，重启机器后自动拉起（systemd `Restart=always`）
- [ ] 每个接口都有实测记录（curl / 脚本），不是"应该能用"
- [ ] 异常路径也测了：空数据、超大文件、中文路径、并发请求
- [ ] 日志里没有反复报错

前端：
- [ ] 5 个页签都能开，控制台零报错
- [ ] 每个按钮点下去**有反馈**（不是点了没反应）
- [ ] 每个面板都有**关闭方式**（× 或返回）
- [ ] 深色/浅色主题都看一遍
- [ ] 手机尺寸（390×844）下不溢出、不挤压

App：
- [ ] 断网能打开外壳
- [ ] 版本号只有一个出处，**不会出现"已是最新还提示更新"**
- [ ] 返回键逐层退，不会一步跳回首页

## 3. 反注水规矩（我的监督重点）

- 不许"复制一个文件改个名字"充数
- 不许留空函数 / 假实现 / `TODO: 以后再说`
- 不许把同一个东西写两遍（**曾经前端里有两套水波纹实现，点一下冒两个圈**——
  这种重复就是典型事故来源）
- 写完自己搜一遍有没有死代码，删掉
- 报告里**不许**出现"基本完成""应该没问题""理论上可行"这种话，
  要么跑通了，要么说清卡在哪

## 4. 工作节奏

- **一轮做一大块**，做透再停，别做一点就汇报
- 遇到选择自己拍板，记进 `docs/决策记录.md`
- 别问用户"你想怎么做"——他不懂技术，也讨厌被问细节；
  要问就问"要不要现在切换到新后端"这种**是非题**，我来转达
- **不许停**：这一轮做完，立刻开始下一轮，直到 `GOAL.md` 里所有条目都打勾

## 5. 现在就要做的第一件事

**先别写代码。** 按顺序产出这三份：
1. `docs/参考项目分析.md`（见第五份的要求）
2. `docs/设计方案.md`：后端架构、数据模型、接口清单、目录结构、技术选型
3. `docs/实施计划.md`：拆成若干轮，每轮目标 + 验收点

三份都写完、我确认过，再动手写第一行代码。
